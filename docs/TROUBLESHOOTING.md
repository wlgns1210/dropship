# 트러블슈팅 기록

만들면서 실제로 막혔던 것들. 증상과 원인이 어긋나 있어 시간을 쓴 것 위주로
남긴다. 고친 방법보다 **왜 늦게 발견했는지**가 더 오래 쓸모 있었다.

---

## 1. 성공한 것처럼 보이는 실패

가장 비싼 부류다. 오류가 나면 거기서부터 찾으면 되는데, 이쪽은 찾을 단서가
없다. 셋 다 "정상" 이라는 신호를 보면서 한참을 헤맸다.

### CRLF 한 글자가 설치 스크립트를 통째로 건너뛰게 했다

**증상** — 파일 권한을 640 으로 조이는 수정을 배포했는데 권한이 그대로 644 였다.
`install.sh` 는 오류 없이 끝났다.

**원인** — 스크립트가 7번째 줄 `set -euo pipefail` 에서 죽고 있었다. Windows 에서
편집하면서 줄바꿈이 CRLF 가 되어 bash 가 `pipefail\r` 을 옵션 이름으로 읽었다.
`invalid option name` 한 줄을 내고 조용히 끝났다.

**고침** — `.gitattributes` 에 `* text=auto eol=lf` 를 넣고 CRLF 가 섞인 22개 파일을
되돌렸다.

**교훈** — systemd 유닛과 nginx 설정도 같은 위험이 있다. CR 이 값의 일부로 해석돼
경로나 옵션이 조용히 어긋난다. 크로스 플랫폼으로 편집하는 저장소는 줄바꿈을
먼저 고정해야 한다.

### `/admin` 이 404 화면을 띄우는데 배포 점검은 통과했다

**증상** — 관리자 페이지 자리에 "페이지를 찾을 수 없습니다" 가 떴다. 파일도 API 도
정상 배포돼 있었다.

**원인** — 두 겹이었다.

1. Next 정적 내보내기는 `/admin` 을 `admin/index.html` 이 아니라 **`admin.html`** 로
   만든다. nginx `try_files` 에 `$uri.html` 이 없어 404 폴백으로 떨어졌다.
2. **그런데 점검은 통과했다.** 이 서비스는 매칭되지 않는 경로를 전부 `404.html` 로
   돌려주면서 **200 을 낸다** — 공유 링크를 살리기 위한 의도된 설계다. 상태 코드만
   보는 점검에서 `/admin → 200` 은 아무 증거가 되지 못했다.

**고침** — `try_files $uri $uri.html $uri/ /404.html`. 그리고 `deploy/verify.sh` 를
만들어 **본문으로** 확인하게 했다. 관리자 화면처럼 클라이언트에서 그려지는
페이지는 정적 HTML 에 최종 문구가 없으므로, 그 페이지 전용 청크를 참조하는지로
판별한다. 폴백에 관리자 청크가 섞이지 않는지도 함께 본다.

**교훈** — 200 이 "페이지가 떴다" 를 뜻하지 않는 설계라면, 점검도 그에 맞춰야 한다.
2번이 1번보다 심각한 문제였다.

### 이름을 바꾸다 TLS 블록이 사라졌는데 서비스는 "정상" 이었다

**증상** — Dropship → Skiff 이전 후 사이트가 전혀 응답하지 않았다. `systemctl status`
는 전부 active 였다.

**원인** — 443 서버 블록이 빠진 채 80 블록의 HTTPS 리다이렉트만 남았다. 80 이
HTTPS 로 넘기는데 받아줄 쪽이 없었다. 프로세스는 멀쩡하니 모든 상태 표시가
정상이었다.

**고침** — `install.sh` 에 가드를 넣었다. TLS 리다이렉트는 있는데 443 서버 블록이
없으면 경고한다.

**교훈** — "프로세스가 살아 있다" 와 "서비스가 응답한다" 는 다른 질문이다.
헬스체크는 뒤쪽을 물어야 한다.

## 2. 보안 — 실제로 공격해서 재현한 것

배포된 서버를 직접 공격해 재현한 뒤 고치고, 재시도해 차단을 확인했다.

### [치명] 헤더 하나로 레이트리밋과 일일 쿼터가 완전히 무력화됐다

**공격** — `CloudFront-Viewer-Address` 를 매 요청 다른 값으로 보냈다. 요청마다 새
신원이 되어 **12회 연속 통과**했다. 레이트리밋도 일일 5GB 쿼터도 의미가 없었다.

**원인** — 이 헤더는 CloudFront 가 덮어써 주기 때문에만 믿을 수 있다. 단일 EC2
구성에는 CloudFront 가 없고 nginx 가 클라이언트 헤더를 그대로 통과시켰다.
"CloudFront 뒤에 있다" 는 전제가 코드에 적혀 있지 않았다.

**고침** — 두 겹으로 막았다.
- 앱이 배포 형태를 보고 **CloudFront 뒤일 때만** 이 헤더를 읽는다.
- nginx 도 해당 헤더를 빈 값으로 덮어 오리진에 보내지 않는다.

`X-Forwarded-For` 는 **마지막** 값을 쓴다. 첫 값을 쓰면 같은 방식으로 뚫린다 —
프록시는 뷰어가 보낸 XFF 를 지우지 않고 뒤에 실제 IP 를 덧붙이기 때문이다.

**교훈** — 신뢰의 근거가 구성에 있다면, 그 구성을 코드가 알아야 한다.

### [높음] "1바이트" 라고 신고하고 8MB 를 올렸다

**공격** — 파일 크기를 1바이트로 신고해 쿼터를 1바이트만 쓰고, 발급받은 파트
URL 로 8MB 를 밀어넣는 데 성공했다. `complete` 를 부르지 않으면 pending 상태로
디스크에 그대로 남는다.

**원인** — 파트 업로드 토큰이 대상만 가리키고 **크기 한도를 담고 있지 않았다.**

**고침** — 파트 토큰에 그 파트가 받을 수 있는 최대 바이트를 함께 서명한다.
서명 안에 있으니 클라이언트가 고칠 수 없고, 실제 업로드량은 항상 쿼터에 반영된
선언량 이하가 된다. 재시도하면 413 이고, 정상 크기 업로드는 그대로 동작한다.

### 업로드 파일과 DB 가 644 로 누구나 읽을 수 있었다

암호화 상태를 점검하다 발견했다. 다른 사용자로 실제 읽기가 됐다. DB 에는
`owner_token`(있으면 남의 전송을 지울 수 있다)과 모든 파일명이 들어 있다.

systemd 유닛에 `UMask=0027` 을 넣어 이후 생성 파일을 640, 디렉터리를 750 으로
고정했다. nginx 는 같은 그룹에 속해 있어 640 으로도 `X-Accel-Redirect` 로 읽는다 —
**권한을 조이다 다운로드가 죽지 않는지 확인하는 것**이 이 수정의 핵심이었다.

## 3. 로컬에서는 되고 배포에서만 깨지는 것

### S3 서명이 배포에서만 틀렸다

**증상** — 로컬(LocalStack)에서는 멀쩡한데 실제 S3 에서 `SignatureDoesNotMatch`.

**원인** — `addressing_style` 이 `"auto"` 였다. auto 는 레거시 글로벌 엔드포인트로
가서 307 리다이렉트를 받는데, 리다이렉트를 따라가면 서명이 깨진다. LocalStack 은
path style 을 쓰므로 이 경로를 아예 지나지 않아 로컬에서는 절대 재현되지 않았다.

**고침** — 실제 AWS 면 `"virtual"`, 커스텀 엔드포인트(LocalStack)면 `"path"`.
회귀 테스트로 고정했다.

### 깨끗한 CI 에서만 실패한 Lambda 패키지 검증

EC2 에서는 venv 에 `boto3` 가 있어 통과했지만 CI 러너에는 없어
`ModuleNotFoundError` 가 났다. boto3 는 Lambda 런타임이 제공하므로 패키지에 넣지
않는데, 검증 단계는 그 런타임을 흉내 내야 해서 임포트는 가능해야 한다.

CI 에 설치 단계를 추가하고, `build_lambda.py` 가 boto3 부재를 "패키지가 잘못됐다"
가 아니라 **"검증 환경이 덜 갖춰졌다"** 로 구분해 알리게 했다.

### 컨테이너에서 앱이 기동조차 못 했다

`config.py` 가 `.env` 를 `parents[3]` 이라는 **고정 깊이**로 찾고 있었다. 컨테이너에
`/app/app/config.py` 로 놓이자 그 깊이가 존재하지 않아 `IndexError` 가 났다.
설정을 읽기도 전에 죽으니 로그에 단서도 없었다.

위로 거슬러 올라가며 찾도록 바꿨다. 파일이 하나도 없어도 정상이다 — 컨테이너와
systemd 배포에서는 환경 변수로 값이 들어오고 `.env` 는 개발 편의 수단일 뿐이다.

### 서비스가 기동하지 못했다 — uvicorn 이 `[dev]` 에만 있었다

Lambda 에서는 ASGI 서버가 필요 없어 기본 의존성이 아니었는데, 단일 노드는
상주 서버가 필요하다. `[server]` 그룹으로 분리했다.

## 4. 테스트가 환경에 좌우된 것

### `/tmp` 가 955MB 라 관계없는 테스트가 무더기로 503 을 받았다

디스크 포화 방어(여유 2GB 미만이면 503)를 넣었더니, 이 머신의 `/tmp` 이 955MB
tmpfs 라 `pytest tmp_path` 의 여유가 기준에 못 미쳤다. 디스크와 무관한 테스트들이
전부 503 으로 떨어졌다.

conftest 에서 검사를 기본적으로 끄고, **가드 자체를 검증하는 테스트만** 여유 값을
명시적으로 고정한다.

### `.env` 값이 테스트에 새어 들어왔다

로컬 `.env` 의 `ADMIN_TOKEN` 이 읽혀 "토큰이 없으면 관리자 라우터가 등록되지
않는다" 는 테스트가 개발자 머신에서만 다르게 돌았다. conftest 에서 관련 값을
명시적으로 빈 문자열로 설정하고, 픽스처 정리도 `delenv` 가 아니라
`setenv(..., "")` 로 한다 — 지우면 `.env` 값이 다시 드러나기 때문이다.

## 5. 타입이 계약을 막고 있던 것

`LocalSigner` 가 `S3Storage` 로 타입이 못 박혀 있어 `LocalStorage` 를 재사용하지
못했고, 단일 노드 모드에서 **다운로드가 500 으로 죽었다.**

구조적 `Protocol`(`SupportsPresign`)로 바꾸고, 두 구현이 같은 계약을 지키는지
계약 테스트로 고정했다. 배포 형태를 두 가지로 유지하는 설계에서는 이런 결합이
한 쪽에서만 터진다.

## 6. 요청이 아예 도착하지 않는 것

컨테이너는 healthy, `curl localhost` 는 200, 로그에는 아무것도 없는데 밖에서만
안 되는 상황. 로그에 단서가 없는 이유는 **요청이 도착하지 않아서**다.

### 예전에 깔아둔 Caddy 가 80/443 을 쥐고 있었다

`ss -tlnp` 에 `127.0.0.1:2019` — Caddy 관리 API 기본 포트였다. Caddyfile 이 엉뚱한
호스트명을 보고 있어 인증서를 30일 동안 재시도하는 중이었고, 그 상태에서 80 은
HTTPS 로 308 을 보내고 443 은 핸드셰이크에서 죽었다. 밖에서 보면 "서버가 아예
없는 것" 과 구분되지 않는다.

### 게이트웨이가 포트 번호를 바꿔서 전달했다

| 외부 | 실제 도착지 |
|------|-------------|
| `25133` | VM 의 **80** |
| `24133` | VM 의 **22** (SSH) |
| `80`·`443` | 게이트웨이 자신 (VM 까지 오지 않음) |

`SKIFF_PORT=25133` 으로 두면 컨테이너는 VM 의 25133 에 붙는데 외부 25133 은 VM 의
80 으로 들어온다. 아무도 닿지 못한다.

**매핑을 확정하는 방법**은 앞단을 잠깐 멈춰보는 것이다. 멈췄을 때 응답이
사라지는 포트가 이 VM 까지 오는 포트다.

### 그 환경에서는 ACME 가 원리상 불가능하다

Let's Encrypt 는 도메인이 가리키는 IP 의 80(HTTP-01) 또는 443(TLS-ALPN-01)으로만
검증한다. 그 두 포트가 게이트웨이에서 끝나면 VM 까지 오지 않는다. **포트를 바꿔
우회할 수 없다.** DNS-01 챌린지를 쓰거나, 게이트웨이가 TLS 를 끝내주거나,
터널을 써야 한다.

### `docker ps` 의 포트 표기

```
0.0.0.0:8090->80/tcp
         ↑      ↑
   바깥에서    컨테이너 안에서만
   닿는 포트    쓰이는 포트
```

`curl http://localhost` 는 80 을 부른다. 컨테이너가 전부 healthy 인데
`Connection refused` 가 나면 거의 이 혼동이다. 두 번 걸렸다.

## 7. nginx 설정에서 조용히 어긋난 것

### `location /` 이 중복되어 nginx 가 기동하지 못했다

TLS 를 붙이며 80 번 블록이 리다이렉트 설정과 앱 설정을 둘 다 include 하게 됐다.
80 번 블록이 읽는 디렉터리를 **하나로** 정리했다 — TLS 가 꺼져 있으면 앱 설정,
켜져 있으면 리다이렉트 설정.

### ACME 챌린지를 SPA 폴백이 먼저 잡았다

`try_files ... /404.html` 이 `/.well-known/acme-challenge/` 요청까지 삼켜 토큰
대신 앱 셸을 돌려줬고 인증서 발급이 실패했다. 해당 location 에 `^~` 를 붙여
우선순위를 올렸다.

### 설정 파일을 복사해두면 한쪽만 고치게 된다

80/443 블록이 앱 라우팅을 각자 갖고 있으면 반드시 한쪽만 고치는 일이 생긴다.
`X-Accel-Redirect` 의 internal 경로가 한쪽에만 있으면 **그쪽에서만 다운로드가
죽는다.** 라우팅을 `nginx-app.inc` 하나로 빼고 양쪽이 include 하게 했다.
컨테이너 이미지도 같은 파일을 쓴다.

## 8. 문서가 틀려서 막힌 것

문서도 코드처럼 틀린다. 아래는 문서대로 따라 하다 막힌 것들이다.

### 복붙 블록 가운데에 손으로 하는 단계가 숨어 있었다

```bash
python3 -c "...print('IP_HASH_SALT='+...)"   # 화면에 찍기만 한다
# 출력을 .env 에 넣고 ...                      ← 손으로 옮기는 단계
```

블록 전체가 복사해 붙여넣게 생겼는데 가운데가 수동이었다. 그대로 따라 하면
`.env` 가 빈 채로 남아 compose 가
`required variable IP_HASH_SALT is missing a value` 로 거절한다.

`sed` 로 `.env` 에 직접 쓰게 바꿨다. 옮기는 단계가 사라지고, 비밀값이 터미널
스크롤백과 셸 기록에 남지도 않는다.

### `curl -o .env` 가 기존 설정을 덮어쓴다

이미 그 VM 에서 돌리고 있었다면 `URL_SIGNING_KEY` 가 사라지고, 다음 `up -d` 에서
**이미 발급된 공유 링크가 전부 죽는다.** 전용 디렉터리에서 하도록 바꾸고,
갱신할 때는 compose 파일만 받는 별도 절차를 적었다.

### 점검 스크립트의 기본 포트가 문서와 어긋났다

`verify.sh` 기본값이 `http://localhost`(80)인데 `SKIFF_PORT` 기본값은 8090 이었다.
인자 없이 돌리면 11줄이 전부 FAIL 로 쏟아져 **정작 원인이 그 속에 묻혔다.**

기본값을 맞추고, 연결 자체가 안 되면 점검을 시작하지 않고 그 사실만 말하게 했다.

### 문서는 실행해봐야 검증된다

위 세 개는 전부 **문서에 적힌 그대로 실행해보지 않으면 못 보는** 결함이다.
내가 확인할 때는 `sed` 로 자동 치환하고 포트를 직접 지정해서 함정을 지나쳤다.
빈 디렉터리에서 문서 단계를 그대로 돌려 스모크 11개와 실제 12MiB 왕복이
통과하는 것까지 확인하고 나서야 이것들이 드러났다.

## 9. 기능을 늘리면서 반쪽만 고친 것

파일 개수 상한을 20 → 100 으로 올려놓고 수신 화면은 파일마다 버튼 하나인 채로
두었다. **100개를 받으려면 100번 눌러야 했다.**

ZIP 일괄 받기를 만들며 정한 것:

- **압축하지 않는다(`ZIP_STORED`).** 오가는 파일 대부분이 이미 압축된
  형식(jpg, mp4, pdf)이라 재압축은 크기를 거의 못 줄이고 CPU 만 쓴다.
- **메모리에 쌓지 않는다.** 100MB 로 실측했을 때 첫 바이트가 0.02초에 나왔다 —
  버퍼링됐다면 전체를 만든 뒤에야 나온다.
- **되감기(seek)를 쓰지 않는다.** 싱크에 `seek` 을 일부러 두지 않아 `zipfile` 이
  data descriptor 방식으로 쓰게 했다. 응답 스트림은 뒤로 갈 수 없다.
- 같은 이름은 `이름 (2).확장자` 로 가른다. ZIP 안의 중복 이름은 압축 해제
  프로그램마다 동작이 갈린다.
- ZIP 생성은 파일 전체를 읽는 비싼 작업이라 **짧은 수명 토큰(5분)으로 보호한다.**
  코드만 알면 바로 호출되게 두면 코드 하나로 서버를 묶어둘 수 있다.

## 10. 방어가 없던 자리 — 디스크 포화

파일 서비스가 죽는 가장 흔한 방식인데 아무 방어가 없었다. 다 차면 업로드가
500 으로 실패하고 사용자는 이유를 모르며, SQLite 쓰기까지 막혀 이미 올라간
파일의 메타데이터도 갱신되지 않는다.

세션 생성 시 `여유 - 요청크기 < 2GB` 면 503 으로 거절한다. 실제로 디스크를 채워
확인했다 — 여유 1.6GB 에서 거절, 공간이 돌아오자 즉시 재개.

**검사를 쿼터 차감보다 먼저 한다.** 공간이 없어 어차피 못 받을 업로드에 쿼터를
깎으면 사용자는 올리지도 못한 채 그날 한도만 잃는다.

관리자 화면에는 사용률(%) 대신 **'업로드 수용' 여부**를 넣었다. 16GB 의 80% 와
1TB 의 80% 는 남은 양이 전혀 다르다. 서버가 실제로 쓰는 판단을 그대로 보여준다.

## 되짚어보면

반복해서 나온 패턴 셋:

**1. 실패가 성공처럼 보이면 비용이 몇 배로 뛴다.** CRLF, `/admin` 404, 사라진
TLS 블록 — 셋 다 "정상" 신호를 보면서 헤맸다. 헬스체크와 점검이 **무엇을
증명하는지** 정확히 알아야 한다. 상태 코드 200 은 이 서비스에서 아무것도
증명하지 못했다.

**2. 신뢰의 전제는 코드에 적어야 한다.** `CloudFront-Viewer-Address` 를 믿을 수
있는 건 CloudFront 뒤일 때뿐인데 그 전제가 코드에 없었다. 구성이 바뀌자 그대로
뚫렸다.

**3. 환경 차이는 가장 늦게, 가장 나쁜 곳에서 드러난다.** S3 서명은 운영에서만,
boto3 는 CI 에서만, `.env` 깊이는 컨테이너에서만 터졌다. 로컬에서 통과하는 것은
증거가 아니라 **가설**이다.
