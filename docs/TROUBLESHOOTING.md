# 설계 판단과 장애 기록 — 단일 노드 배포

익명 파일 전송 서비스를 서버리스에서 **단일 노드**(nginx + uvicorn + 로컬 디스크
\+ SQLite)로 옮기면서 내린 판단과, 그 과정에서 실제로 터진 것들.

옮기는 작업의 본질은 "같은 기능을 다른 인프라로" 가 아니었다. **관리형 서비스가
대신 지켜주던 보장들이 한꺼번에 사라지는 일**이었다. DynamoDB 의 조건부 업데이트,
CloudFront 가 덮어써 주던 헤더, S3 의 무한한 용량 — 이것들이 없어진 자리를 하나씩
메워야 했고, 안 메운 자리가 그대로 취약점이 됐다.

---

## 1. 앞단이 바뀌자 레이트리밋이 통째로 뚫렸다

서버리스에서는 안전했던 코드가 그대로 취약해진 사례다. **직접 공격해서 재현했다.**

### 공격

`CloudFront-Viewer-Address` 헤더를 매 요청 다른 값으로 보냈다. 요청마다 새 신원이
되어 **12회 연속 통과**했다. 레이트리밋도 일일 5GB 쿼터도 의미가 없었다.

### 왜 안전하다고 믿었나

이 헤더는 CloudFront 가 **뷰어가 보낸 값을 덮어쓰기** 때문에 신뢰할 수 있다.
그 전제 위에서 쓰고 있었는데, 전제가 코드 어디에도 적혀 있지 않았다. 앞단을
nginx 로 바꾸자 클라이언트 헤더가 그대로 통과했다.

### 고침 — 두 겹

```python
def client_ip(request, *, behind_cloudfront: bool = False) -> str:
    if behind_cloudfront:                      # 믿을 수 있는 구성일 때만
        viewer = request.headers.get("cloudfront-viewer-address")
        if viewer:
            return _strip_port(viewer.strip())

    forwarded = request.headers.get("x-forwarded-for")
    if forwarded:
        hops = [h.strip() for h in forwarded.split(",") if h.strip()]
        if hops:
            return hops[-1]                    # 첫 값이 아니라 마지막 값
    ...
```

- 앱이 배포 형태를 인자로 받아 **믿을 수 있는 구성일 때만** 읽는다.
- nginx 도 해당 헤더를 빈 값으로 덮어 오리진에 보내지 않는다.

`X-Forwarded-For` 를 **마지막** 값으로 읽는 것도 같은 이유다. 프록시는 뷰어가 보낸
XFF 를 지우지 않고 **뒤에** 실제 IP 를 덧붙인다. 첫 값을 믿으면 헤더 한 줄로 매번
다른 신원을 만들 수 있다. 가장 가까운 신뢰 프록시가 덧붙인 마지막 값만 믿을 수 있다.

> **교훈** — 신뢰의 근거가 인프라 구성에 있다면, 그 구성을 코드가 알아야 한다.
> 주석으로 적는 것으로는 부족하다. 구성이 바뀌는 순간 아무도 그 주석을 보지 않는다.

## 2. 선언한 크기와 실제 업로드가 묶여 있지 않았다

### 공격

파일 크기를 **1바이트**라고 신고해 쿼터를 1바이트만 소비하고, 발급받은 파트
업로드 URL 로 **8MB** 를 밀어넣는 데 성공했다. `complete` 를 부르지 않으면
pending 상태로 디스크에 그대로 남는다. 쿼터를 거의 쓰지 않고 디스크를 채울 수 있다.

### 원인

파트 업로드 토큰이 **대상만** 가리키고 있었다. 어디에 쓸지는 정해져 있는데
얼마나 쓸 수 있는지는 정해져 있지 않았다.

### 고침 — 한도를 토큰에 서명해 넣는다

```python
def part_bytes(number: int) -> int:
    return max(0, min(PART_SIZE, size - (number - 1) * PART_SIZE))

part_urls = [
    "/api/upload/" + local_tokens.sign(
        self._secret,
        {"k": key, "p": number, "n": filename, "m": mime, "s": part_bytes(number)},
        url_ttl,
    )
    for number in range(1, part_count_for(size) + 1)
]
```

크기가 서명 안에 있으니 클라이언트가 고칠 수 없고, **실제 업로드량은 항상 쿼터에
반영된 선언량 이하**가 된다. 재시도하면 413 이고 정상 크기 업로드는 그대로 동작한다.

> S3 presigned URL 은 이 제약을 서명 정책에 담을 수 있다. 직접 만든 토큰으로
> 갈아타면서 **무엇이 서명에 들어 있어야 하는지**를 다시 따져야 했는데, 대상만
> 옮기고 한도를 빠뜨렸다.

## 3. 조건부 업데이트가 사라진 자리 — 쿼터 경합

DynamoDB 는 조건부 업데이트로 "읽고-판단하고-쓰기" 를 원자적으로 처리해 준다.
SQLite 로 옮기면서 이 보장이 사라졌다.

그냥 옮기면 **동시에 들어온 두 요청이 각자 잔여량을 읽고 둘 다 통과**한다.
하루 한도를 넘겨서 올릴 수 있다.

```python
connection.execute("BEGIN IMMEDIATE")   # 읽기 전에 쓰기 잠금을 먼저 잡는다
try:
    row = connection.execute(
        "SELECT bytes_used FROM quotas WHERE ip_hash = ? AND day = ?", (ip_hash, day)
    ).fetchone()
    used = row["bytes_used"] if row else 0
    if used + num_bytes > DAILY_QUOTA_BYTES:
        connection.execute("ROLLBACK")
        ...
```

`BEGIN` 이 아니라 `BEGIN IMMEDIATE` 인 것이 핵심이다. 기본 `BEGIN` 은 지연
트랜잭션이라 첫 읽기 시점에는 잠금을 잡지 않는다. 레이트리밋도 같은 구조다.

연결 설정에서 함께 정한 것:

| PRAGMA | 이유 |
|---|---|
| `journal_mode=WAL` | 기본 모드는 쓰기가 읽기를 통째로 막는다. 업로드 확정 한 건이 수신자 조회를 전부 대기시킨다 |
| `busy_timeout=15000` | 잠금이 잡혀 있으면 즉시 실패하지 말고 기다린다 |
| `synchronous=NORMAL` | WAL 에서 충분히 안전하면서 fsync 횟수를 줄인다 |

## 4. 무한했던 용량이 유한해졌다

S3 에는 용량 한도가 없어 생각할 필요가 없던 고장 모드다. 로컬 디스크에 쌓기
시작하면서 생겼고, **방어가 아무것도 없었다.**

다 차면 업로드가 500 으로 실패하고 사용자는 이유를 모른다. 더 나쁜 건 SQLite
쓰기까지 막혀 **이미 올라간 파일의 메타데이터도 갱신되지 않는다**는 점이다.

### 검사 위치가 중요했다

```python
free = storage.free_bytes()
if free is not None and free - total_size < DISK_HEADROOM_BYTES:
    raise HTTPException(status_code=503, detail="서버 저장 공간이 부족합니다...",
                        headers={"Retry-After": "3600"})
```

이 검사를 **쿼터 차감보다 먼저** 한다. 순서가 반대면, 공간이 없어 어차피 받지도
못할 업로드 때문에 사용자가 그날 한도만 잃는다. 올리지도 못했는데.

`free_bytes()` 가 `None` 을 돌려주면 호출부가 검사를 건너뛴다 — S3 구현이 그렇다.
이 제약은 로컬 디스크에만 있으므로 인터페이스에서 "해당 없음" 을 표현할 수 있어야 했다.

### 관리자 화면에는 % 대신 판단을 보여준다

사용률만으로는 "지금 업로드를 받을 수 있는가" 에 답할 수 없다. **16GB 의 80% 와
1TB 의 80% 는 남은 양이 전혀 다르다.** 서버가 실제로 쓰는 기준을 그대로 노출했다.

```json
{"accepting_uploads": true, "disk_headroom_bytes": 2147483648}
```

실제로 디스크를 채워 확인했다 — 여유 1.6GB 에서 거절, 공간이 돌아오자 즉시 재개.

## 5. 두 구현을 유지하려면 계약을 테스트해야 한다

단일 노드 모드에서 **다운로드가 500 으로 죽었다.** 원인은 `LocalSigner` 가
`S3Storage` 로 타입이 못 박혀 있어 `LocalStorage` 를 받지 못한 것이었다.

저장소를 인터페이스 뒤에 두고 두 구현을 유지하는 설계인데, **한쪽만 아는 타입이
하나 끼어 있으면 그쪽에서만 터진다.** 타입 검사는 통과했다 — 잘못된 것을 정확히
표현하고 있었기 때문이다.

구조적 `Protocol` 로 바꾸고, 두 구현이 같은 계약을 지키는지 **계약 테스트**로
고정했다. 어느 구현을 넣어도 같은 테스트가 돌아야 한다.

## 6. 정리 코드가 리눅스에서 우연히 동작하고 있었다

파트를 이어붙이다 실패하면 임시 파일(`.assembling`)을 지운다. 그 정리가
`with` 블록 **안**에 있었다.

```python
with temporary.open("wb") as output:
    for number in numbers:
        source = self.part_path(key, number)
        if not source.exists():
            temporary.unlink(missing_ok=True)   # 파일이 아직 열려 있다
            raise FileNotFoundError(...)
```

리눅스는 열린 파일도 unlink 되므로 통과한다. 그래서 **더 큰 문제가 가려져
있었다** — 정리가 "파트 누락" 경로에만 있어서, 이어붙이는 도중 디스크가 차면
(`ENOSPC`) `.assembling` 이 그대로 남았다.

디스크 포화는 이 서비스가 따로 방어할 만큼 흔한 고장인데, 하필 그때 찌꺼기가
쌓여 **남은 공간을 더 깎는 방향**으로 움직였다.

```python
try:
    with temporary.open("wb") as output:
        ...
except BaseException:
    temporary.unlink(missing_ok=True)   # 핸들이 닫힌 뒤
    raise
```

`with` 밖으로 옮기니 쓰기 실패 전체를 받는다. 이식성 문제를 고치려다 실제
자원 누수를 찾은 경우다.

## 7. 100개를 받으려면 100번 눌러야 했다

파일 개수 상한을 20 → 100 으로 올려놓고 수신 화면은 파일마다 버튼 하나인 채로
두었다. 기능을 늘리면서 받는 쪽을 고치지 않았다.

ZIP 일괄 받기를 만들며 정한 것들:

**압축하지 않는다 (`ZIP_STORED`)** — 오가는 파일 대부분이 이미 압축된
형식(jpg, mp4, pdf)이다. 재압축은 크기를 거의 못 줄이고 CPU 만 쓴다. 단일 노드는
CPU 한 개짜리라 이 선택이 곧바로 응답 지연으로 나타난다.

**되감기를 쓰지 않는다** — 응답 스트림은 뒤로 갈 수 없다. `zipfile` 은 중앙
디렉터리를 쓸 때 앞으로 되돌아가려 하는데, 싱크에 `seek` 을 **일부러 정의하지
않아** `AttributeError` 를 보고 data descriptor 방식으로 쓰게 했다.

```python
class _Sink:
    """``seek`` 을 일부러 정의하지 않는다. zipfile 이 AttributeError 를 보고
    "되감을 수 없는 스트림" 으로 판단해 data descriptor 를 쓰게 하기 위해서다."""
```

**메모리에 쌓지 않는다** — 쓰는 즉시 내보내고 버퍼를 비운다. 100MB 로 실측했을 때
첫 바이트가 0.02초에 나왔다. 버퍼링됐다면 전체를 만든 뒤에야 나온다.

**짧은 수명 토큰(5분)으로 보호한다** — ZIP 생성은 파일 전체를 읽는 비싼 작업이다.
코드만 알면 바로 호출되게 두면 **코드 하나로 서버를 묶어둘 수 있다.** 코드 검증과
레이트리밋을 통과한 사람만 토큰을 받는다.

이 경로에서만 파일 바이트가 Python 을 지난다. 단일 파일은 여전히 nginx 가
`X-Accel-Redirect` 로 직접 보낸다.

## 8. 배포 점검이 아무것도 증명하지 못하고 있었다

`/admin` 자리에 "페이지를 찾을 수 없습니다" 가 떴다. 원인 자체는 단순했다 —
Next 정적 내보내기는 `/admin` 을 `admin/index.html` 이 아니라 **`admin.html`** 로
만드는데 nginx `try_files` 에 `$uri.html` 이 없었다.

**문제는 배포 점검이 이걸 통과시켰다는 것이다.**

이 서비스는 매칭되지 않는 경로를 전부 `404.html` 로 돌려주면서 **200 을 낸다.**
공유 링크(`/oslo/113245`)를 정적 배포에서 살리기 위한 의도된 설계다. 그래서
상태 코드만 보는 점검에서 `/admin → 200` 은 **아무 증거가 되지 못했다.**

점검을 본문 기반으로 바꿨다. 관리자 화면처럼 클라이언트에서 그려지는 페이지는
정적 HTML 에 최종 문구가 없으므로, **그 페이지 전용 청크를 참조하는지**로 판별한다.
폴백에 관리자 청크가 섞이지 않는지도 함께 본다.

```
[페이지 — 본문으로 확인]
  OK   업로드 화면 /           (끌어다 놓으세요 포함)
  OK   관리자 화면 /admin      (chunks/app/admin/page- 포함)
  OK   공유 링크 폴백          (chunks/app/not-found- 포함)
  OK   폴백/관리자 분리
```

> **교훈** — 200 이 "페이지가 떴다" 를 뜻하지 않는 설계를 골랐다면, 점검도 그에
> 맞춰야 한다. 버그보다 **버그를 통과시킨 점검**이 더 심각한 문제였다.

같은 이유로 "프로세스가 살아 있다" 와 "서비스가 응답한다" 를 구분하게 됐다.
한 번은 nginx 의 443 블록이 빠진 채 80 블록의 HTTPS 리다이렉트만 남아 사이트가
전혀 응답하지 않았는데, `systemctl status` 는 전부 `active` 였다.

## 9. 권한을 조이는 것과 기능을 죽이는 것 사이

암호화 상태를 점검하다 발견했다. 업로드 파일과 SQLite DB 가 **644 로 만들어져
누구나 읽을 수 있었다.** 다른 사용자 계정으로 실제 읽기가 됐다. DB 에는
`owner_token`(있으면 남의 전송을 지울 수 있다)과 모든 파일명이 들어 있다.

`UMask=0027` 로 640/750 을 강제하는 것 자체는 한 줄이다. **어려운 건 이걸
조이면서 다운로드를 죽이지 않는 것이었다.**

다운로드는 nginx 가 `X-Accel-Redirect` 로 파일을 직접 읽어 보낸다. 640 이면
소유자와 그룹만 읽는다. nginx 를 같은 그룹에 넣어야 한다.

컨테이너로 옮기면서 이 제약이 다시 나타났다. api 와 web 이 **다른 이미지**인데
같은 볼륨을 공유한다. 두 이미지에서 GID 를 10001 로 고정했다.

```dockerfile
RUN groupadd -g 10001 skiff \
 && useradd -u 10001 -g 10001 -M -s /usr/sbin/nologin skiff
```

이 마운트나 GID 를 빠뜨리면 **화면은 멀쩡히 뜨는데 다운로드만 404 가 난다.**

## 10. 인증서를 받을 수 없는 네트워크

도메인을 사지 않고 TLS 를 붙여야 했다. Let's Encrypt 는 **IP 주소에는 인증서를
발급하지 않는다.** `sslip.io` 가 호스트명에 든 IP 를 그대로 돌려주는 와일드카드
DNS 라, `15.164.209.152.sslip.io` 로 진짜 인증서를 받았다. 자가서명이 아니라
브라우저 경고가 없다.

나중에 NAT 뒤 VM 으로 옮기면서 이 방법이 **원리상 불가능**해지는 상황을 만났다.

ACME 검증은 도메인이 가리키는 IP 의 **80(HTTP-01) 또는 443(TLS-ALPN-01)** 으로만
온다. 게이트웨이가 그 두 포트를 자기가 처리하고 VM 에는 다른 포트만 넘기면,
포트를 바꿔 우회할 방법이 없다. DNS-01 챌린지를 쓰거나, 게이트웨이가 TLS 를
끝내주거나, 터널을 써야 한다.

nginx 설정에서 함께 정리한 것:

- **앱 라우팅을 파일 하나로 빼고 80/443 블록이 함께 include 한다.** 복사해두면
  반드시 한쪽만 고치는 일이 생기는데, `X-Accel-Redirect` 의 internal 경로가
  한쪽에만 있으면 **그쪽에서만 다운로드가 죽는다.** 컨테이너 이미지도 같은 파일을 쓴다.
- **ACME 챌린지 location 에 `^~` 를 붙인다.** 없으면 SPA 폴백
  (`try_files ... /404.html`)이 먼저 잡아 토큰 대신 앱 셸을 돌려주고 발급이 실패한다.

## 되짚어보면

**관리형 서비스는 기능이 아니라 보장을 판다.** 옮기면서 사라진 것은 API 가 아니라
보장이었다 — 조건부 업데이트(원자성), 헤더 덮어쓰기(신뢰), 무한한 용량. 기능은
금방 대체했지만 보장은 하나씩 직접 세워야 했고, 안 세운 자리가 취약점이 됐다.
두 취약점 모두 **이 전환에서 생겼다.**

**검증이 무엇을 증명하는지 알아야 한다.** `/admin` 버그 자체는 `try_files` 한 줄
이었다. 진짜 문제는 그걸 통과시킨 점검이었고, 그 점검은 이 서비스의 설계에서
구조적으로 아무것도 증명할 수 없었다. 통과하는 테스트는 증거가 아니라 **가설**이다.

**옵션 하나가 곧 판단이다.** `BEGIN` 과 `BEGIN IMMEDIATE`, `journal_mode` 기본과
WAL, `umask` 022 와 027, `seek` 을 정의하느냐 마느냐 — 기본값을 그냥 두면 대부분의
경우에 동작하고 **경계에서만** 틀린다. 그 경계가 동시 요청이고 디스크 포화이고
남의 계정이다.
